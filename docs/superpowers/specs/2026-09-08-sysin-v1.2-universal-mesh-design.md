# SysIn V1.2 Universal + Mesh — Design

## Status

Owner-approved design direction on 2026-09-08. This document records the locked SysIn V1.2 product, architecture, UX, Mesh, security, migration, testing, and certification authority before implementation planning begins.

No V1.2 implementation work is authorized by this document alone. The Owner must review and approve this written specification before an implementation plan is created.

## Governing quality rule

SysIn V1.2 is PASS only when every applicable certification category individually scores exactly 10.0/10, every mandatory requirement is verified, no material finding remains unresolved, and the Owner approves the exact release candidate on real hardware.

- 10.0/10 in every applicable category -> eligible for PASS.
- Any category below 10.0 -> HOLD.
- Unknown or untested requirement -> HOLD.
- Unresolved material defect -> HOLD.
- An average such as 9.7/10 can never compensate for a lower category.

Visual certification is independent from functionality, telemetry correctness, interaction, performance, accessibility, security/privacy, reliability/recovery, packaging/update, platform compatibility, CLI/schema, diagnostics, migration, and real-machine acceptance.

If Mesh is included or marketed as Stable in a release, Mesh certification categories are applicable and must also reach 10.0/10. Local SysIn may reach Stable while Mesh remains Preview/HOLD, but that release must not present Mesh as Stable.

# 1. Product Constitution

## 1.1 Identity

# SYSIN

Official meanings:

1. **System Info**
2. **SYStem INsight**
3. **See Your System In Numbers**
   - S — See
   - Y — Your
   - S — System
   - I — In
   - N — Numbers

Official catchphrase:

> **Every machine. One command. Total insight.**

Universal command:

```text
sysin
```

## 1.2 Product definition

SysIn is a universal, native, colorful, high-performance system-insight platform for understanding one computer or an explicitly authorized collection of computers through a consistent terminal UI, CLI, telemetry model, visual language, and diagnostic language.

Its primary responsibilities are:

> **observe -> understand -> explain -> diagnose -> compare -> retain bounded history -> export trustworthy evidence**

SysIn is observation-first. It is not primarily a system-control product.

## 1.3 Product character

SysIn should feel professional, powerful, colorful, fast, alive, technical, approachable, trustworthy, power-user capable, and universal across independently certified platforms.

It must not feel sterile, cluttered, fake-futuristic, like uncontrolled RGB decoration, debug-looking, or misleading.

## 1.4 First-class experiences

One normalized system model serves three surfaces:

### Local interactive dashboard

```text
sysin
```

Opens the responsive Spectrum terminal UI.

### CLI / machine-readable interface

Examples:

```text
sysin cpu
sysin gpu
sysin doctor
sysin snapshot
sysin snapshot --json
```

The CLI is a first-class compatibility surface for humans, scripts, agents, diagnostics, and integrations.

### SysIn Mesh

When Mesh is explicitly enabled and multiple authenticated devices belong to the same authorized account context, SysIn can expose a multi-machine dashboard.

Local SysIn remains usable without an account, internet access, or Mesh.

## 1.5 Local-first doctrine

Normal local SysIn must not require:

- an account;
- internet access;
- cloud telemetry;
- a background service merely to use the dashboard;
- administrator privileges;
- PowerShell as the product runtime.

Mesh is explicit opt-in networked functionality. Enabling Mesh authorizes only the telemetry allowed by the device’s Mesh privacy policy.

This design does **not** authorize a hidden always-on Mesh service/agent. Initial Mesh telemetry is available while an explicitly started SysIn Mesh host/session is active unless a future optional background agent is separately designed and Owner-approved.

## 1.6 Explicit non-goals

V1.2 is not authorized to become, without a separate future design:

- an overclocking/undervolting suite;
- a fan-control or hardware-tuning utility;
- a destructive Task Manager replacement;
- a benchmark suite;
- a generic OS repair utility;
- a remote shell or remote desktop;
- an arbitrary remote command executor;
- a kernel-driver ecosystem;
- an open third-party plugin marketplace;
- a cloud surveillance platform.

# 2. Universal Technical Architecture

## 2.1 Architectural north star

```text
Platform / Hardware
        |
Platform + Vendor Providers
        |
Capability Resolver
        |
Typed Metric Observations
        |
Telemetry Engine
   /       |        \
History   Alerts   Diagnostics
   \       |        /
     SystemSnapshot
      /     |      \
Local TUI  CLI   SysIn Mesh
```

Governing boundary:

> **Providers know how to measure. Telemetry knows what is true. Views know how to present. Mesh knows what may leave the machine.**

## 2.2 Runtime foundation

V1.2 replaces the V1.1 PowerShell product runtime with a native C# / modern .NET architecture.

The runtime must be self-contained where practical, async/cancellation-aware, modular without needless fragmentation, provider-oriented, testable without every physical hardware combination, least-privilege by default, and universal in its core contracts.

Windows x64 is the first reference implementation because it is the current live migration/test target. Windows-specific APIs must remain below universal interfaces.

PowerShell may remain useful for Windows bootstrap or migration tooling but is not the V1.2 product runtime.

NativeAOT may be evaluated later; it is not required if it reduces provider compatibility or correctness.

## 2.3 Logical module boundaries

```text
SysIn/
├── src/
│   ├── SysIn.App
│   ├── SysIn.Core
│   ├── SysIn.Telemetry
│   ├── SysIn.Providers
│   ├── SysIn.Platform.Windows
│   ├── SysIn.Platform.Linux
│   ├── SysIn.Platform.MacOS
│   ├── SysIn.Provider.Nvidia
│   ├── SysIn.Provider.Amd
│   ├── SysIn.Provider.Intel
│   ├── SysIn.Provider.Apple
│   ├── SysIn.History
│   ├── SysIn.Alerts
│   ├── SysIn.Diagnostics
│   ├── SysIn.Configuration
│   ├── SysIn.Export
│   ├── SysIn.Terminal
│   ├── SysIn.Views
│   ├── SysIn.Cli
│   ├── SysIn.Update
│   ├── SysIn.Account
│   └── SysIn.Mesh
├── tests
├── packaging
└── docs
```

These are logical ownership boundaries, not a requirement for one assembly per name. The implementation plan may combine modules when interfaces remain clear and independently testable.

## 2.4 Composition root

`SysIn.App` should parse arguments, detect platform/terminal capabilities, load approved providers, compose dependencies, select interactive/CLI/Mesh mode, run the application, and guarantee cleanup.

It must not contain telemetry implementation, provider-specific measurement logic, rendering internals, or business rules.

## 2.5 Universal metric vocabulary

Canonical metric identities are semantic rather than platform API names. Examples:

```text
cpu.utilization
cpu.frequency
cpu.temperature
cpu.power

gpu.utilization
gpu.temperature
gpu.power
gpu.memory.used
gpu.clock.core

memory.physical.used
memory.available
memory.pressure

storage.read.rate
storage.write.rate
storage.active_time
storage.latency

network.receive.rate
network.transmit.rate
```

Platform/vendor providers translate native measurements into these canonical metrics.

## 2.6 Typed observations and truth states

Conceptual observation:

```text
MetricObservation
├── MetricId
├── DeviceId
├── Value
├── Unit
├── ObservedAt
├── ProviderId
├── Quality
├── Freshness
└── Availability
```

Availability/freshness states include at least:

- Fresh
- Aging
- Stale
- Unsupported
- Unavailable
- PermissionRequired
- ProviderError

Hard rule:

> **Unknown is not zero.**

A valid zero measurement may never be used as a placeholder for missing telemetry.

## 2.7 Device identity

Stable internal device identity is separate from human-readable names.

SysIn distinguishes CPU/topology, GPUs, physical storage devices, logical volumes, network adapters, sensors, batteries, and other supported hardware classes.

Every GPU is independently enumerated. Integrated and discrete GPUs remain distinct devices with distinct history/provenance. SysIn must not invent a combined GPU percentage.

Evidence-backed roles may include integrated, discrete, display, and high-performance.

## 2.8 Provider registry and trust

Providers declare capabilities rather than UI pages.

Capability resolution preference:

1. trusted direct vendor/native source;
2. trusted platform-native source;
3. audited generic fallback;
4. explicit Unsupported/Unavailable.

Provider trust classes distinguish platform/native APIs, official vendor APIs/SDKs, bundled audited third-party libraries, and explicitly optional external providers.

Experimental providers must not silently outrank certified providers.

V1.2 must not use unsafe arbitrary DLL search, arbitrary remote provider-code download, or an open plugin marketplace.

## 2.9 Collector supervision and device changes

Each collector runs independently with cadence, timeout, cancellation, execution-time measurement, retry/backoff, health state, and circuit breaker.

A slow provider must not block the renderer or unrelated telemetry.

Fresh values age to stale/unavailable rather than remaining visually live forever.

OS/device events should trigger targeted rediscovery when available; low-frequency reconciliation catches missed events. Sleep/resume, docking, network adapter change, GPU driver reset, and device arrival/removal are first-class recovery scenarios.

## 2.10 Immutable snapshot pipeline

Collectors publish observations into a telemetry store. A snapshot builder creates coherent `SystemSnapshot` instances for consumers.

```text
SystemSnapshot
├── System
├── Cpu[]
├── Gpus[]
├── Memory
├── Storage[]
├── Network[]
├── Processes[]
├── Sensors[]
├── Alerts[]
├── ProviderHealth[]
└── SysInHealth
```

Views and CLI consume snapshots or derived view models, not raw providers.

## 2.11 Independent clocks

Rendering, local telemetry sampling, and Mesh synchronization are separate clocks.

- Balanced render target defaults to 20 FPS.
- Fast metrics may sample several times per second.
- Expensive sensors sample more slowly and are cached.
- Static identity refreshes on discovery/change or low cadence.
- Mesh machine-list summaries use lower rates than local rendering.
- Active remote inspection may request a temporarily higher permitted cadence.

The UI displays measured actual FPS separately from target FPS.

## 2.12 Performance discipline

SysIn must minimize observer effect.

Engineering targets on a typical modern machine include:

- average steady-state CPU around <=1.0% in normal Overview, preferably <=0.5% where practical;
- working set <=100 MB where realistic for selected runtime/providers;
- no busy-wait render loops;
- perceived input response roughly <50 ms;
- explicit collector performance budgets;
- measured frame-build/diff/write time, dropped frames, actual FPS, SysIn process CPU/memory, provider overruns.

These are engineering targets, not universal hardware guarantees. Before RC, each certified target must have an explicit measured performance budget; it may not be silently waived. Any platform-specific adjustment requires documented evidence and Owner approval.

Adaptive load control may reduce expensive sampling or optional animation, but must never falsify telemetry.

Performance profiles:

- Eco
- Balanced — default
- Realtime

## 2.13 History

History stores canonical metric/device/timestamp data before UI formatting.

Logical live windows include at least 10s, 30s, 60s, 5m, and 15m.

Persistent local history is optional, local, bounded, size-limited, retention-limited, auto-pruned, and erasable. Session-first is the default.

## 2.14 Evidence-based alerts

Activity and health severity are independent dimensions.

Severity classes include Normal, Info, Elevated, Warning, Critical, and Unknown.

High utilization alone is not necessarily unhealthy. Evidence such as thermal throttling, sustained critical storage pressure, memory pressure, or provider failure can drive severity.

Alerts carry affected machine/device, condition, severity, evidence, first-seen time, duration, last update, and resolution state where applicable.

Arbitrary health scores are forbidden unless a rigorously defined evidence-backed formula is separately approved.

# 3. Terminal UI and UX Authority

## 3.1 Purpose-built TUI engine

SysIn uses a focused TUI engine rather than making Spectre.Console or Terminal.Gui the core dashboard framework.

Required capabilities:

- terminal capability detection;
- alternate-screen lifecycle;
- guaranteed terminal restoration;
- framebuffer;
- differential rendering;
- responsive layout;
- keyboard input;
- optional mouse input/hit testing/scrolling;
- semantic theme engine;
- virtual-terminal testing.

The renderer builds a desired frame, compares it with the prior frame, and writes only changed regions where practical.

## 3.2 Terminal lifecycle

Interactive `sysin` uses alternate screen where supported. Exit, Ctrl+C, cancellation, or unexpected failure must restore screen, cursor, mouse mode, colors/styles, and input mode.

Noninteractive commands use normal stdout.

An explicit inline mode may be provided.

Redirected output must never receive cursor control. JSON stdout must contain JSON only; diagnostics go to stderr.

## 3.3 Capability tiers

- Tier 3 / Premium — true color, Unicode, mouse, alternate screen, full responsive motion.
- Tier 2 / Standard — VT-capable with reduced visual complexity.
- Tier 1 / Compatibility — safe characters, simpler graphics, keyboard-first, reduced color.
- Tier 0 / Noninteractive — plain/structured output without ANSI cursor control.

Detection is capability-based, not merely terminal-name based.

## 3.4 Visual direction

The approved V1.2 direction is a balanced hybrid of mockups 2 and 3:

- mockup 2 for structure, navigation clarity, and utility organization;
- mockup 3 for personality, command-deck energy, header/footer presence, and dynamic rhythm;
- substantially greater color richness than either original mockup.

Target: professional + powerful + modern + exciting, at balanced information density.

## 3.5 SysIn Spectrum Engine

Subsystem families:

| Subsystem | Spectrum family |
| --- | --- |
| CPU | deep blue -> electric blue -> cyan |
| GPU | emerald -> green -> aqua |
| Memory | violet -> purple -> magenta |
| Storage | amber -> orange -> gold |
| Network | cyan -> aqua -> turquoise |
| Processes | gold -> yellow -> lime |

Status semantics remain independent:

- Healthy — green with explicit status cues
- Info — blue
- Elevated — yellow
- Warning — orange
- Critical — red
- Unknown — neutral with explicit symbol/text

Because GPU identity and Healthy may both use green-family hues, status must also use symbols, labels, tone, placement, and accessibility cues; hue alone never carries critical meaning.

Color may appear in panel tints, borders, icons, chart lines/fills, gauges, navigation, focus, keycaps, metric emphasis, badges, and activity indicators.

Hard rule:

> **Activity intensity != danger severity.**

A healthy GPU at 100% may become visually energetic within the GPU palette without turning red.

## 3.6 Strong subsystem identity

CPU, GPU, Memory, Storage, Network, and Processes should be visually recognizable before the user reads the title through coordinated tint, accent rail, icon, graph palette, gauge palette, focus glow, and interaction states.

The dashboard must not become identical dark rectangles with tiny colored labels.

## 3.7 Motion and reduced motion

Purposeful B++ micro-animation may include smooth chart progression, value/gauge interpolation, live-state pulses, brief warning/recovery transitions, short page/focus transitions, and subtle active-panel emphasis.

Forbidden: strobing, gratuitous blinking, particle effects, motion that hides latency, harms readability, or violates performance budgets.

Reduced-motion mode removes nonessential animation while preserving accurate updates.

## 3.8 Accessibility

Accessibility is built into components.

Important state uses multiple channels: text, symbols, position, patterns/markers, and focus affordances in addition to color.

The architecture supports high contrast, color-blind-safe variants, reduced motion, visible focus, full keyboard navigation, and mouse as optional enhancement only.

## 3.9 Canonical screen anatomy

At large sizes:

```text
Living Command Header
├── Left Navigation Sidebar
├── Main View
└── Context / Attention Rail
Global Hotkey Command Bar
```

Header may show SYSIN, current page, Live/Paused state, performance profile, actual/target FPS, uptime, Admin only when elevated, degraded-provider count when relevant, and remote identity/data age when viewing another machine.

## 3.10 Navigation

Canonical page map:

```text
Overview
CPU
GPU
Memory
Storage
Network
Processes
Sensors
Doctor
Machines
Settings
Help / About
```

Keyboard-first with direct page hotkeys where practical, arrows/Enter, `P` pause, `Q` quit, `/` command palette/search, and documented shortcuts. Mouse is supported where terminal capabilities allow, but no core function requires it.

## 3.11 Responsive modes

- XL Command Deck
- Large Dashboard
- Medium Focused Dashboard
- Compact Essential Monitor
- Minimum-safe state

Panels can resize, stack, collapse secondary detail, shorten labels, reduce chart history width, and move the context rail.

Below minimum-safe dimensions, SysIn displays a clear resize/snapshot message rather than a mangled layout.

Hard anti-regression rule:

> **Never strand a tiny dashboard in the upper-left of a large terminal with huge dead space.**

## 3.12 Overview

Overview answers: **What is happening right now?**

Three layers:

1. Live Summary Ribbon — CPU, all relevant GPUs, RAM, Storage, Network, Uptime, renderer context.
2. Adaptive Asymmetric Command Grid — larger charts for information-rich areas; medium/smaller supporting panels.
3. Context / Attention Rail — alerts, hardware, top activity, provider/SysIn health.

Layout locations stay stable; severity changes emphasis, not geometry.

## 3.13 Detail pages

### CPU

Total history, topology, P/E-core or other heterogeneous-core distinctions, per-core/logical utilization where available, frequency, trustworthy temperature/power, throttling, top contributors, min/avg/max, provenance details.

### GPU

Every GPU independently enumerated; selected-device focus; Compare mode; utilization, VRAM/shared-memory semantics, temperature, clocks, power, fans, engines, provenance/freshness, explicit N/A.

### Memory

Physical used/available, commit, cache, page file, composition, pressure history, top consumers, platform-normalized deeper details. High utilization alone is not automatically a warning.

### Storage

Physical device != logical volume. Physical devices may expose throughput, active time, latency, temperature, supported SMART/health evidence. Volumes expose capacity/free/used/file system. No invented health scores.

### Network

Adapter-aware state, download/upload rates, session totals, link speed, Wi-Fi signal, errors/drops, VPN and multiple adapters. Normal Overview/default snapshots avoid unnecessary full IP/MAC/SSID/remote endpoint exposure.

### Processes

Sortable/filterable live table, process tree, PID, runtime/start, CPU/GPU/memory/disk/network where available, thread count, GPU engine, expandable inspector with history. Sensitive command lines/environment/user/full paths are not prominent by default. Destructive process controls are not a V1.2 primary feature.

### Sensors

Human-normalized hierarchical temperature/fan/power/battery explorer with original provider identity available in technical details.

## 3.14 Doctor

Doctor is the unified trust center for runtime, renderer, providers, devices, config, updater/integrity, permissions, terminal, history, and Mesh.

Every problem must explain:

1. What failed?
2. Why?
3. What is affected?
4. What can the user do?

Optional missing sensors can legitimately be Partial without implying the whole product failed.

## 3.15 Universal command palette

`/` searches pages, devices, metrics, processes, settings, commands, machines, and help. It may navigate or run safe actions but may not bypass authorization/confirmation boundaries.

## 3.16 Settings and profiles

One validated config model is shared by interactive Settings, CLI, and config file.

Areas include appearance, performance, telemetry, history, alerts, accessibility, profiles, Mesh, privacy, updates, and advanced diagnostics.

Malformed config must not prevent SysIn from starting; it must recover to safe defaults/repair state and explain the problem.

Named profiles include concepts such as Balanced, Gaming, Diagnostics, Low Power, and custom profiles. Exports must not blindly embed secrets or device-specific sensitive identities.

# 4. CLI, Structured Output, Snapshots, and Diagnostics

## 4.1 CLI grammar

Common commands remain concise:

```text
sysin
sysin cpu
sysin gpu
sysin memory
sysin storage
sysin network
sysin processes
sysin sensors
sysin doctor
sysin snapshot
```

Hierarchy where useful:

```text
sysin config get|set|reset
sysin update check|install|rollback
sysin history status|clear
sysin logs show|clear
```

Aliases may exist, but help identifies canonical forms. Unknown commands provide helpful suggestions rather than parser dumps.

## 4.2 Structured output

Examples:

```text
sysin snapshot --json
sysin gpu --json
sysin doctor --json
sysin capabilities --json
```

Structured output preserves schema version, timestamp, device IDs, units, provenance, freshness, quality/status, and provider health where relevant.

JSON stdout is valid JSON only. Diagnostics go to stderr. Exit codes carry machine-readable outcome.

## 4.3 Snapshot evidence

Snapshots are point-in-time evidence artifacts, not terminal screenshots.

Conceptual forms:

```text
sysin snapshot
sysin snapshot --json
sysin snapshot --markdown
sysin snapshot --save
```

They may include timestamp, version/schema, platform, CPU/GPU/memory/storage/network, selected processes/sensors, provider health, provenance/freshness, alerts, and SysIn performance.

Default snapshots avoid unnecessary private data. A richer diagnostic export must clearly disclose the additional data class.

## 4.4 Diagnostic journal

SysIn may keep a small local bounded journal for startup/shutdown, provider init/failure, timeouts/circuit-breakers, renderer failure, config migration, update result, and unexpected exceptions.

It must not become an unbounded telemetry log or silently capture sensitive process content.

Logs are local, rotating, size/retention limited, and erasable. Deep tracing is explicit per-session.

## 4.5 Notifications

In-dashboard alerts are default. OS notifications are optional and off by default unless explicitly enabled.

Notification logic requires deduplication, cooldown, escalation/resolution tracking, and sustained-condition behavior to avoid alert storms.

## 4.6 Privilege model

Normal SysIn runs as a standard user.

Metrics requiring extra privilege report PermissionRequired. Elevation is explicit, temporary, capability-specific, and visibly indicated.

No silent elevation, permanent policy change, or default kernel-driver installation is authorized.

# 5. SysIn Mesh: Account, Privacy, and Security

## 5.1 Mesh role

Mesh extends system insight across explicitly authorized machines without weakening local-first behavior.

The Machines dashboard may aggregate independently certified Windows, macOS, and Linux systems under one account context. A remote view uses the same SysIn design language but must always make machine identity, Remote state, connection/data age, and stale/offline status obvious.

## 5.2 Account and email semantics

An account is required for Mesh, not for local SysIn.

Email may identify/authenticate the account, but email alone is never device identity or authorization.

```text
Email != authorization
Same Wi-Fi != authorization
Hostname != identity
LAN presence != trust
```

## 5.3 Enrollment and cryptographic device identity

Conceptual flow:

```text
Verified Account
      |
Authenticated Enrollment
      |
Unique Device Identity + Device Credential
      |
Explicit Authorization
      |
Mesh Membership
```

Each device has independent cryptographic credentials and is independently revocable.

Private device key material remains protected on-device using appropriate platform-secure facilities where available. Established TLS/crypto primitives are required; no custom cryptographic protocol.

Friendly names/hostnames are separate from stable identity.

## 5.4 Connection paths

Mesh may use encrypted direct/LAN and authenticated relay/internet paths behind one authorization contract.

LAN proximity changes routing, not trust. No unauthenticated local metrics endpoint is permitted merely because devices share a network.

## 5.5 Remote projection allowlist

Raw local `SystemSnapshot` must not be uploaded wholesale by default.

```text
SystemSnapshot
      |
RemoteProjection
      |
Privacy Allowlist
      |
Mesh Telemetry Envelope
      |
Authenticated/Encrypted Transport
```

Only explicitly allowed fields may leave the machine.

Normal Mesh summary may include CPU/GPU/memory/storage/network summary rates, selected sensors, alerts, provider/SysIn health, platform/hardware model, and presence/last-seen.

Normal Mesh overview does not require full IP/MAC addresses, usernames, process command lines, environment variables, file paths, open files, remote endpoints, browser data, or document names.

## 5.6 Per-device visibility

Each device may allow/deny categories such as System Summary, CPU, GPU, Memory, Storage, Network Rates, Processes, Sensors, History, and Diagnostic Details.

## 5.7 Adaptive remote cadence

Mesh does not stream local 20-FPS render data.

- machine list -> low-rate summary;
- opened machine -> medium detail;
- opened subsystem -> temporarily higher permitted detail;
- page closed -> cadence drops.

## 5.8 Remote freshness/offline/history

Remote metrics expose measurement/data age. Stale values are explicitly marked.

Offline machines show last-seen time. Last-known identity may remain; old telemetry may not appear live.

Remote history policies support None, Summary, and Detailed. Summary is the recommended default when history is enabled. Retention is bounded and deletable.

## 5.9 Device removal, revocation, and sessions

Device removal must revoke credentials, terminate active sessions, stop accepting telemetry, remove authorization, and apply the selected history retention/deletion policy.

A revoked device continues to support local SysIn.

Account sessions must be visible/revocable where implemented. Credential rotation must not unnecessarily change stable DeviceId/history.

## 5.10 Observation-only remote protocol

The first Mesh protocol contains no generalized remote execution channel.

It does not define arbitrary shell execution, command execution, process kill, restart/shutdown, file mutation, or hardware tuning endpoints.

This is a protocol-level boundary, not a hidden UI toggle.

## 5.11 Failure isolation

Mesh/account/relay/internet/remote-device failure must never prevent local SysIn from functioning. Only networked functionality degrades.

## 5.12 Future authorization extensibility

Although initial Mesh usage is same-account devices, authorization should conceptually ask whether a principal may view a device instead of scattering direct account-ID equality throughout the code. This leaves future family/team/read-only sharing possible without shipping those features now.

## 5.13 Mesh security tests

Mesh certification includes invalid credentials, revoked-device reconnect, replayed enrollment, expired/revoked sessions, malformed/oversized telemetry, unexpected metric types, stale/replayed telemetry, relay outage, LAN impersonation, credential rotation, device removal during connection, and privacy-field leakage.

Security failures fail closed.

# 6. Installation, Migration, Update, and Release Engineering

## 6.1 V1.1 relationship

V1.1 PowerShell remains the known functional migration/proof-of-concept baseline while V1.2 is built beside it.

Do not mutate V1.1 incrementally into a mixed PowerShell/C# runtime that jeopardizes the known-good install path.

## 6.2 Build sequence

Recommended vertical order:

1. Native executable shell and CLI composition root.
2. Universal telemetry contracts and device/metric model.
3. Windows x64 reference providers.
4. TUI framebuffer/diff renderer/capability engine.
5. Overview.
6. CPU/GPU/Memory.
7. Storage/Network/Processes/Sensors.
8. Doctor/Settings/Command Palette.
9. History/Alerts/Snapshots/structured output.
10. Installer/migration/update/rollback.
11. Additional platform providers/certification.
12. Mesh account/enrollment/remote projection/Machines dashboard.
13. Full release certification.

The implementation plan may decompose these steps further but may not violate dependency boundaries.

## 6.3 Universal platform strategy

Universal design begins immediately; certification is per platform/RID.

Potential artifact families as implemented and certified:

```text
win-x64
win-arm64
linux-x64
linux-arm64
osx-x64
osx-arm64
```

Compilation alone does not confer support.

## 6.4 Packaging and supply-chain integrity

A release package may include:

```text
sysin executable
approved provider/native dependencies
licenses
release metadata
```

Stable artifacts carry version, channel, platform/RID, commit provenance, SHA-256, dependency/license inventory, schema version, certification state, and signing status where applicable.

Stable release engineering should generate an SBOM.

Rules:

- every shipped artifact is hash-verified;
- published release metadata/bytes are immutable;
- dependency versions are pinned;
- no arbitrary runtime download of mystery DLLs;
- no PATH-dependent product runtime requirement;
- no silent replacement of immutable published release bytes;
- signing is used where the platform/release infrastructure supports/requires it;
- preview may be unsigned but must never claim signed status.

## 6.5 Version/channel/build/certification semantics

These are separate concepts.

Channels:

- Nightly
- Preview
- Release Candidate
- Stable

Examples:

```text
1.2.0-preview.1
1.2.0-rc.1
1.2.0
```

Stable means published, immutable, verified, and fully certified for the applicable target. It never means merely that an updater points at a branch.

Published `v1.2.0` bytes never change; fixes use a new version such as `v1.2.1`.

## 6.6 Transactional update

```text
Resolve release
-> validate manifest
-> download exact artifact
-> verify hash/signature
-> stage separately
-> pre-activation validation
-> atomic activation
-> bounded post-activation health check
-> commit update
```

Failure before commit triggers rollback where safely possible. Never overwrite the only known-good executable before replacement is verified.

A version-separated install layout may be used as long as atomic activation, rollback, version identity, and unknown-file safety are preserved.

## 6.7 V1.1 -> V1.2 migration

Migration must:

1. detect V1.1;
2. validate known files/config;
3. preserve a known-good backup;
4. migrate supported config through schema-aware migration;
5. stage native V1.2;
6. verify it;
7. activate atomically;
8. run bounded post-activation health checks;
9. preserve rollback where possible.

Preserve compatible safe settings/current-user command registration. Do not blindly preserve obsolete runtime files, stale manifests, incompatible keys, or unknown executables as official components.

Unknown user files must never be recursively deleted simply because they are in a SysIn directory.

Rollback restores prior known-good runtime/config activation metadata without silently destroying newer user data.

## 6.8 Update failure matrix

Tests cover interrupted download, wrong hash, corrupt/truncated artifact, invalid/incomplete manifest, wrong RID/version, invalid required signature, disk full, locked files, activation failure, config migration failure, post-startup health failure, and rollback failure.

Every case must leave a safe understandable state.

## 6.9 Exact published-byte verification

Stable verification hashes the exact bytes users download, not merely local checkout bytes. This is a permanent release doctrine learned from V1.1's published-byte/line-ending integrity failure.

## 7.8 Provider and platform certification

Provider states may include Certified, Preview, Experimental, Unavailable.

Universal architecture does not imply simultaneous Stable status.

Example:


## 7.9 Mesh certification

## 7.11 Security/privacy certification

Known unresolved security/privacy defects block release.
