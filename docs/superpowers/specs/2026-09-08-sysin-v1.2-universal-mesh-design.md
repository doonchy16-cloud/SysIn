# SysIn V1.2 Universal + Mesh — Design

## Status

Owner-approved design direction on 2026-09-08. This document records the locked SysIn V1.2 product, architecture, UX, Mesh, security, migration, testing, and certification authority before implementation planning begins.

No V1.2 implementation work is authorized by this document alone. The written specification must be reviewed and approved by the Owner before an implementation plan is created.

## Governing quality rule

SysIn V1.2 is PASS only when every applicable certification category individually scores exactly 10.0/10, every mandatory requirement is verified, no material finding remains unresolved, and the Owner approves the actual release candidate on real hardware.

- 10.0/10 in every applicable category -> eligible for PASS.
- Any category below 10.0 -> HOLD.
- Unknown or untested requirement -> HOLD.
- Unresolved material defect -> HOLD.
- An average such as 9.7/10 can never compensate for a lower category.

Visual certification is independent from functional, telemetry, interaction, performance, accessibility, security/privacy, reliability/recovery, packaging/update, platform compatibility, CLI/schema, diagnostics, migration, and real-machine acceptance.

# 1. Product Constitution

## 1.1 Product identity

# SYSIN

Official interpretations:

1. **System Info** — the straightforward practical meaning.
2. **SYStem INsight** — the deeper product meaning.
3. **See Your System In Numbers** — the full five-letter expansion:
   - S — See
   - Y — Your
   - S — System
   - I — In
   - N — Numbers

Official catchphrase:

> **Every machine. One command. Total insight.**

The universal command is:

```text
sysin
```

## 1.2 Product definition

SysIn is a universal, native, colorful, high-performance system-insight platform for understanding one computer or an explicitly authorized collection of computers through a consistent terminal interface, CLI, telemetry model, visual language, and diagnostic language.

Its primary responsibilities are:

> **observe -> understand -> explain -> diagnose -> compare -> retain bounded history -> export trustworthy evidence**

SysIn is observation-first. It is not primarily a system-control product.

## 1.3 Product character

SysIn should feel:

- professional;
- powerful;
- colorful;
- fast;
- alive;
- technical;
- approachable;
- trustworthy;
- power-user capable;
- universal across independently certified platforms.

SysIn must not feel:

- sterile;
- cluttered;
- fake-futuristic;
- like uncontrolled RGB gaming decoration;
- debug-looking;
- misleading.

## 1.4 Three first-class experiences

SysIn exposes one telemetry truth through three primary surfaces.

### Local interactive dashboard

```text
sysin
```

Opens the responsive Spectrum terminal UI.

### CLI and machine-readable interface

Examples:

```text
sysin cpu
sysin gpu
sysin doctor
sysin snapshot
sysin snapshot --json
```

The CLI is a first-class compatibility surface for humans, scripts, agents, diagnostics, and integrations.

### SysIn Mesh

When Mesh is enabled and multiple authenticated devices belong to the same authorized account context, SysIn can expose a multi-machine dashboard. Local SysIn remains usable without an account or Mesh.

## 1.5 Local-first doctrine

Normal local SysIn must not require:

- an account;
- internet access;
- cloud telemetry;
- a background service merely to use the dashboard;
- administrator privileges;
- PowerShell as the runtime.

Mesh is explicit opt-in networked functionality. Enabling Mesh is the authorization boundary that permits selected remote telemetry to leave the machine.

## 1.6 Observation-first non-goals

V1.2 is not authorized to become any of the following without a separate future design:

- overclocking suite;
- undervolting or hardware tuning panel;
- fan-control utility;
- destructive process-management replacement for Task Manager;
- benchmark suite;
- generic Windows/macOS/Linux repair utility;
- remote shell;
- remote desktop;
- arbitrary remote command executor;
- kernel-driver ecosystem;
- open third-party plugin marketplace;
- cloud surveillance platform.

This boundary exists so SysIn can go very deep on trustworthy system insight without shallowly absorbing unrelated system-management capabilities.

# 2. Universal Technical Architecture

## 2.1 Architectural north star

The canonical architecture is:

```text
Platform / Hardware
        |
Platform + Vendor Providers
        |
Capability Resolver
        |
Typed Metric Observations
        |
Telemetry Engine
   /       |        \
History   Alerts   Diagnostics
   \       |        /
     SystemSnapshot
      /     |      \
Local TUI  CLI   SysIn Mesh
```

The governing boundary is:

> **Providers know how to measure. Telemetry knows what is true. Views know how to present. Mesh knows what may leave the machine.**

No layer may silently absorb another layer's responsibility.

## 2.2 Runtime foundation

V1.2 moves from the V1.1 PowerShell runtime to a native C# / modern .NET application architecture.

The runtime must be:

- self-contained for supported release targets where practical;
- async and cancellation-aware;
- modular without unnecessary architectural fragmentation;
- provider-oriented;
- testable without requiring physical hardware for every state;
- least-privilege by default;
- Windows-first in implementation sequence but universal in core contracts.

PowerShell may remain useful for Windows bootstrap or migration tooling, but it is not the V1.2 product runtime.

NativeAOT may be evaluated only after provider and telemetry compatibility are proven. It is not a design requirement if it would reduce correctness or compatibility.

## 2.3 Logical module structure

The intended logical structure is:

```text
SysIn/
├── src/
│   ├── SysIn.App/
│   ├── SysIn.Core/
│   ├── SysIn.Telemetry/
│   ├── SysIn.Providers/
│   ├── SysIn.Platform.Windows/
│   ├── SysIn.Platform.Linux/
│   ├── SysIn.Platform.MacOS/
│   ├── SysIn.Provider.Nvidia/
│   ├── SysIn.Provider.Amd/
│   ├── SysIn.Provider.Intel/
│   ├── SysIn.Provider.Apple/
│   ├── SysIn.History/
│   ├── SysIn.Alerts/
│   ├── SysIn.Diagnostics/
│   ├── SysIn.Configuration/
│   ├── SysIn.Export/
│   ├── SysIn.Terminal/
│   ├── SysIn.Views/
│   ├── SysIn.Cli/
│   ├── SysIn.Update/
│   ├── SysIn.Account/
│   └── SysIn.Mesh/
├── tests/
├── packaging/
└── docs/
```

These are logical boundaries, not permission to create dozens of tiny assemblies. Multiple namespaces may remain in a single assembly when that preserves clear ownership and testability.

## 2.4 Composition root

`SysIn.App` is the composition root. It should:

1. parse startup arguments;
2. detect the current platform and terminal environment;
3. load approved platform/vendor providers;
4. compose dependencies;
5. select interactive, CLI, or Mesh-related mode;
6. run the selected mode;
7. guarantee cleanup and terminal restoration.

It must not contain telemetry implementation, rendering logic, provider-specific details, or business rules.

## 2.5 Universal telemetry vocabulary

Core metric identities must be semantic rather than platform API names. Examples include:

```text
cpu.utilization
cpu.frequency
cpu.temperature
cpu.power

gpu.utilization
gpu.temperature
gpu.power
gpu.memory.used
gpu.clock.core

memory.physical.used
memory.available
memory.pressure

storage.read.rate
storage.write.rate
storage.active_time
storage.latency

network.receive.rate
network.transmit.rate
```

Platform and vendor providers translate native measurements into these canonical metrics.

## 2.6 Metric observation model

Every observation carries enough evidence to answer what was measured, where it came from, when it was measured, and whether it should be trusted.

Conceptually:

```text
MetricObservation
├── MetricId
├── DeviceId
├── Value
├── Unit
├── ObservedAt
├── ProviderId
├── Quality
├── Freshness
└── Availability
```

Availability/freshness states include at least:

- Fresh;
- Aging;
- Stale;
- Unsupported;
- Unavailable;
- PermissionRequired;
- ProviderError.

Hard rule:

> **Unknown is not zero.**

A valid `0` measurement must never be confused with missing or unsupported telemetry.

## 2.7 Device identity

Physical and logical devices receive stable internal identities where reasonably possible. Device identity must be independent of the current human-readable label.

The model distinguishes at least:

- CPU devices/topology;
- GPUs;
- physical storage devices;
- logical volumes;
- network adapters;
- sensors;
- batteries and other supported hardware classes.

A multi-GPU machine must enumerate every GPU independently. SysIn must not invent a combined GPU percentage.

A device may carry roles such as integrated, discrete, display, high-performance, or other evidence-backed roles.

## 2.8 Provider registry and capability resolution

Providers declare capabilities instead of owning UI features.

A provider may state that it can supply, for example:

```text
gpu.utilization      Direct
gpu.temperature      Direct
gpu.power            Direct
gpu.memory.used      Direct
gpu.fan.rpm          Optional
```

Capability resolution should prefer, in order:

1. trusted direct vendor/native source;
2. trusted platform-native source;
3. audited generic fallback;
4. explicit Unsupported/Unavailable state.

Experimental providers must never silently override a certified provider.

Provider trust classes should distinguish platform/native APIs, official vendor APIs/SDKs, bundled audited third-party libraries, and explicitly optional external providers.

V1.2 must not support arbitrary unsafe DLL discovery or remote provider-code downloads.

## 2.9 Collector supervision

Each collector runs independently under supervision with:

- sampling cadence;
- timeout budget;
- cancellation;
- execution-time measurement;
- controlled retry/backoff;
- health state;
- circuit breaker for repeated failure.

A slow or failed provider must not block the render thread or unrelated collectors.

Metric freshness must decay through an explicit lifecycle rather than displaying the last value indefinitely as if it were current.

Sleep/resume, device arrival/removal, network changes, driver reset, docking, and similar events should trigger targeted rediscovery where available, with low-frequency reconciliation as a safety net.

## 2.10 Immutable snapshot pipeline

Collectors publish observations into a telemetry store. A snapshot builder produces coherent immutable-ish `SystemSnapshot` instances for consumers.

Conceptually:

```text
SystemSnapshot
├── System
├── Cpu[]
├── Gpus[]
├── Memory
├── Storage[]
├── Network[]
├── Processes[]
├── Sensors[]
├── Alerts[]
├── ProviderHealth[]
└── SysInHealth
```

Views and CLI output must consume snapshots or derived view models rather than reading providers directly.

## 2.11 Three-clock architecture

Rendering, telemetry sampling, and Mesh synchronization are independent clocks.

- Local render target defaults to 20 FPS.
- Fast telemetry may update several times per second.
- Expensive sensors update more slowly and are cached.
- Static hardware information is refreshed on discovery/change or at a low cadence.
- Mesh summaries use lower remote rates than local rendering.
- Active remote inspection may temporarily request a higher permitted telemetry cadence.

The UI must display measured actual FPS separately from target FPS.

## 2.12 Performance budgets

SysIn must minimize observer effect. Engineering targets for a typical modern machine include:

- average steady-state CPU target around <=1.0% in normal Overview, with a preference around <=0.5% where practical;
- working set target <=100 MB where realistic for the selected runtime/providers;
- no busy-wait rendering;
- perceived input response target under roughly 50 ms;
- every collector has an explicit performance budget;
- renderer measures frame-build time, terminal-write time, dropped frames, and actual FPS;
- SysIn monitors its own process CPU and memory use.

These are engineering targets rather than universal guarantees across every machine. Adaptive load control may reduce expensive sampling or optional animation when required, but it must never falsify telemetry to preserve visual smoothness.

## 2.13 Performance profiles

The architecture supports at least:

- Eco;
- Balanced — default;
- Realtime.

The default render target remains 20 FPS in Balanced mode.

## 2.14 History

History stores canonical metric/device/time data before UI formatting.

Logical live windows include at least:

- 10s;
- 30s;
- 60s;
- 5m;
- 15m.

Persistent local history is optional, bounded, local, configurable, size-limited, retention-limited, automatically pruned, and erasable. Session-first behavior remains the default.

No background service is required merely to preserve the local V1.2 dashboard model.

## 2.15 Alerts

Alerts should be evidence-based and must distinguish activity from health severity.

Severity classes include at least:

- Normal;
- Info;
- Elevated;
- Warning;
- Critical;
- Unknown.

High GPU utilization alone is not a warning. Thermal throttling, sustained critical storage pressure, provider failure, memory pressure, or similarly supported evidence may be.

Alerts carry the affected machine/device, condition, severity, evidence, first-seen time, duration, last update, and resolution state where relevant.

Hardcoded simplistic health scores such as an arbitrary `73/100` are forbidden unless a rigorously defined, evidence-backed metric is introduced later.

# 3. Terminal UI and UX Authority

## 3.1 TUI engine

SysIn uses a focused purpose-built TUI engine rather than making Spectre.Console or Terminal.Gui the architectural core.

The engine includes:

- terminal capability detection;
- alternate-screen lifecycle;
- terminal state restoration;
- framebuffer;
- differential renderer;
- responsive layout engine;
- keyboard input;
- optional mouse input;
- scroll handling;
- hit testing;
- semantic theme system;
- virtual-terminal testing.

The renderer builds the desired frame, compares it with the prior frame, and writes only changed regions where practical.

## 3.2 Terminal ownership

Interactive `sysin` uses the alternate screen when supported. On exit, Ctrl+C, cancellation, or unexpected failure, SysIn must restore:

- previous screen;
- cursor visibility/state;
- mouse mode;
- terminal colors/styles;
- terminal input modes.

Noninteractive commands such as `sysin version`, `sysin doctor`, and `sysin snapshot` use normal stdout.

An explicit inline mode may be offered for environments where alternate-screen operation is not desired.

Redirected output must never receive interactive cursor control. Machine-readable JSON must be clean on stdout; diagnostics go to stderr.

## 3.3 Terminal capability tiers

SysIn detects capabilities rather than merely matching terminal names.

- Tier 3 / Premium: true color, Unicode, mouse, alternate screen, full responsive motion.
- Tier 2 / Standard: VT-capable with reduced visual complexity.
- Tier 1 / Compatibility: safe characters, simpler graphics, keyboard-first operation, reduced color.
- Tier 0 / Noninteractive: plain/structured output with no cursor control or ANSI contamination.

## 3.4 Visual direction

The V1.2 visual direction is a balanced hybrid of the approved Concept 2 and Concept 3 mockups:

- Concept 2 structure, navigation clarity, and utility organization;
- Concept 3 personality, command-deck energy, stronger header/footer presence, and more dynamic visual rhythm;
- substantially greater color richness than either original mockup.

The target is professional + powerful + modern + exciting, with balanced information density.

## 3.5 SysIn Spectrum Engine

Color is semantic and pervasive, not decorative garnish.

Subsystem color families:

| Subsystem | Spectrum family |
| --- | --- |
| CPU | deep blue -> electric blue -> cyan |
| GPU | emerald -> green -> aqua |
| Memory | violet -> purple -> magenta |
| Storage | amber -> orange -> gold |
| Network | cyan -> aqua -> turquoise |
| Processes | gold -> yellow -> lime |

Status semantics are separate from subsystem identity:

- Healthy — green;
- Info — blue;
- Elevated — yellow;
- Warning — orange;
- Critical — red;
- Unknown — neutral/white/gray with explicit symbol/text.

Color may appear in panel tints, borders, icons, chart lines/fills, gauges, navigation, focus states, keycaps, metric emphasis, badges, and activity indicators.

Hard rule:

> **Activity intensity and danger severity are different dimensions.**

A healthy GPU at 100% utilization may become visually energetic inside the GPU palette without turning red.

## 3.6 Strong subsystem identity

CPU, GPU, Memory, Storage, Network, and Processes should be visually recognizable before reading the title. Each subsystem may use its category palette across panel tint, accent rail, icon, chart treatment, gauges, focus glow, and selected-state styling while preserving consistent component geometry.

V1.2 must not regress to identical dark rectangles distinguished only by tiny labels.

## 3.7 Motion

V1.2 uses purposeful B++ micro-animation:

- smooth chart progression;
- gauge/value interpolation;
- live-state pulses;
- brief warning/recovery transitions;
- short page/focus transitions;
- subtle active-panel emphasis.

Forbidden:

- constant strobing;
- decorative particle effects;
- gratuitous blinking;
- motion that hides latency;
- motion that impairs readability;
- animation that violates performance budgets.

Reduced-motion mode removes nonessential motion while preserving accurate data updates.

## 3.8 Accessibility

Accessibility is part of the component system, not an afterthought.

Important states must communicate through more than color: text, symbols, position, patterns/markers, and focus affordances must remain meaningful.

The architecture supports:

- high-contrast presentation;
- color-blind-safe variants;
- reduced motion;
- visible keyboard focus;
- complete keyboard navigation;
- mouse as optional enhancement, never a requirement.

## 3.9 Permanent screen anatomy

At sufficiently large sizes, the canonical layout is:

```text
Living Command Header
├── Left Navigation Sidebar
├── Main View
└── Context / Attention Rail
Global Hotkey Command Bar
```

The header is compact rather than a large decorative banner.

It may show:

- SYSIN branding;
- current page;
- Live or Paused state;
- current performance profile;
- actual/target FPS;
- uptime;
- Admin indicator only when elevated;
- provider-degraded count when relevant;
- Remote indicator and data age when viewing another machine.

## 3.10 Navigation

Primary page map:

```text
Overview
CPU
GPU
Memory
Storage
Network
Processes
Sensors
Doctor
Machines
Settings
Help / About
```

Keyboard-first navigation includes direct page hotkeys where practical, arrows/Enter for navigation, `P` for pause, `Q` for quit, `/` for global command palette/search, and other documented controls. Mouse interaction is supported where the terminal permits it, but no core action requires a mouse.

## 3.11 Responsive layout modes

SysIn uses semantic responsive modes rather than assuming one terminal size:

- XL Command Deck;
- Large Dashboard;
- Medium Focused Dashboard;
- Compact Essential Monitor;
- Minimum-safe state.

Panels may resize, stack, collapse secondary detail, shorten labels, reduce chart history width, and move the context rail beneath the primary content.

Below the minimum-safe size, SysIn must show a clear resize/snapshot message instead of rendering a mangled dashboard.

Hard visual anti-regression rule:

> **SysIn must never again strand a tiny dashboard in the upper-left corner of a large terminal while leaving enormous dead space.**

## 3.12 Overview

Overview answers:

> **What is happening right now?**

Its canonical three-layer composition is:

1. Live Summary Ribbon — CPU, all relevant GPUs, RAM, Storage, Network, Uptime, and render target/actual context as appropriate.
2. Adaptive Asymmetric Command Grid — larger charts for information-rich subsystems and medium/smaller panels for supporting metrics.
3. Context / Attention Rail — Alerts, Hardware, Top Activity, Provider/SysIn Health.

Layout positions remain stable while warning emphasis adapts. Panels should not jump around when a subsystem becomes unhealthy.

## 3.13 CPU page

The CPU deep-dive page supports:

- total utilization history;
- CPU model/topology;
- P-core/E-core or other heterogeneous-core distinctions where applicable;
- per-core/logical utilization where available;
- frequency;
- package temperature/power where trustworthy;
- throttling state where available;
- top CPU contributors;
- min/avg/max history;
- provider provenance on demand.

## 3.14 GPU page

All GPUs are independently enumerated and labeled by evidence-backed role where available.

The dedicated GPU page provides:

- selected-device focus;
- multi-GPU selector;
- instant Compare mode;
- utilization;
- VRAM/shared memory semantics;
- temperatures;
- clocks;
- power;
- fan speed;
- engine activity;
- provider/freshness details;
- explicit `N/A` where metrics are unsupported.

## 3.15 Memory page

The Memory page distinguishes utilization from pressure and may expose:

- physical used/available;
- committed memory;
- cached memory;
- page file;
- composition;
- pressure history;
- top memory users;
- deeper Windows/macOS/Linux memory detail where appropriately normalized.

High utilization alone is not automatically a warning.

## 3.16 Storage page

Storage distinguishes physical devices from volumes.

Physical device views may include:

- read/write throughput;
- active time;
- latency;
- temperature;
- supported SMART/health evidence;
- physical identity.

Volume views may include capacity, free/used space, and file system.

SysIn must not invent arbitrary storage-health scores.

## 3.17 Network page

The Network page is adapter-aware and may expose:

- connected/disconnected state;
- download/upload rate;
- session totals;
- link speed;
- Wi-Fi signal where available;
- errors/drops where supported;
- multiple adapters including VPNs.

Sensitive network identifiers such as full IP addresses, MAC addresses, SSIDs, or remote endpoints are not unnecessarily shown in normal Overview or default snapshots.

## 3.18 Processes page

V1.2 supports powerful process observation with conservative control.

The page may include:

- sortable/filterable live table;
- CPU/GPU/memory/disk/network where available;
- PID;
- process tree;
- start/runtime information;
- thread count;
- GPU engine where available;
- expandable inspector with history graphs.

Command lines, environment data, usernames, full paths, and similarly sensitive details are not exposed prominently by default.

V1.2 does not make process termination, suspend, priority, affinity, or other destructive controls a prominent core feature.

## 3.19 Sensors page

Sensors are presented hierarchically by human-useful categories such as:

- temperatures;
- fans;
- power;
- battery.

Raw provider names should be normalized for humans while preserving original provider identity in technical details.

## 3.20 Doctor

Doctor is the unified trust and diagnostics center.

It evaluates areas such as:

- runtime;
- renderer;
- providers;
- devices;
- configuration;
- updater/integrity;
- permissions;
- terminal capabilities;
- history;
- Mesh.

Every diagnostic problem should answer:

1. What failed?
2. Why?
3. What is affected?
4. What can the user do?

Optional missing sensors may legitimately produce a Partial result without implying the whole product is broken.

## 3.21 Universal command palette

Pressing `/` opens a universal command/search palette capable of finding:

- pages;
- hardware devices;
- metrics;
- processes;
- settings;
- commands;
- machines;
- help topics.

The palette may launch safe navigation/actions but may not bypass permission or confirmation boundaries.

## 3.22 Settings and profiles

Configuration has one validated model shared by interactive settings, CLI, and config file.

Settings cover areas such as:

- appearance;
- performance;
- telemetry;
- history;
- alerts;
- accessibility;
- profiles;
- Mesh;
- privacy;
- updates;
- advanced diagnostics.

A malformed config must not prevent SysIn from starting. SysIn should recover to safe defaults or a clear repair state while explaining the invalid configuration.

Named profiles are supported conceptually, including Balanced, Gaming, Diagnostics, Low Power, and custom profiles. Profiles may control render FPS, sampling cadence, history, visible panels, alert preferences, theme, motion, and default page. Profile export/import must not blindly embed secrets or device-specific sensitive identities.

# 4. CLI, Snapshots, and Structured Data

## 4.1 CLI grammar

Common commands stay concise:

```text
sysin
sysin cpu
sysin gpu
sysin memory
sysin storage
sysin network
sysin processes
sysin sensors
sysin doctor
sysin snapshot
```

Hierarchy is used where it adds clarity:

```text
sysin config get
sysin config set
sysin config reset

sysin update check
sysin update install
sysin update rollback

sysin history status
sysin history clear

sysin logs show
sysin logs clear
```

Aliases may exist, but help must identify one canonical spelling.

Unknown commands should produce helpful suggestions rather than parser dumps.

## 4.2 Structured output

Noninteractive data commands may provide stable structured output over the same normalized telemetry model, including:

```text
sysin snapshot --json
sysin gpu --json
sysin doctor --json
sysin capabilities --json
```

Structured output preserves, where relevant:

- schema version;
- timestamp;
- device IDs;
- units;
- provenance;
- freshness;
- quality;
- explicit status states;
- provider health.

JSON stdout must contain valid JSON only. Human diagnostics belong on stderr. Exit codes carry machine-readable outcome.

## 4.3 Snapshot system

Snapshots are point-in-time evidence artifacts, not merely pretty terminal dumps.

Supported conceptual forms include:

```text
sysin snapshot
sysin snapshot --json
sysin snapshot --markdown
sysin snapshot --save
```

Snapshots may capture:

- timestamp;
- SysIn version/schema;
- OS/platform;
- CPU;
- GPU devices;
- memory;
- storage;
- network;
- selected process/sensor summaries;
- provider health;
- provenance/freshness;
- active alerts;
- SysIn performance.

Default snapshots avoid unnecessary private data. A more detailed diagnostic snapshot, if provided, must clearly disclose the additional data class before sharing/export.

# 5. SysIn Mesh, Account, Privacy, and Security

## 5.1 Mesh product role

SysIn Mesh extends local SysIn across explicitly authorized machines. It must not weaken local-first behavior.

The Machines dashboard can aggregate independently certified Windows, macOS, and Linux machines under one authorized account context.

A remote machine view uses the same SysIn visual language, but the UI must make remote context obvious, including machine identity, remote state, connection/data age, and stale/offline status.

## 5.2 Account requirement

An account is required for Mesh, not for local SysIn.

The account may use email as a verified login/account identifier. Email alone is never a device credential or authorization mechanism.

Hard rule:

```text
Email != authorization
Same Wi-Fi != authorization
Hostname != identity
LAN presence != trust
```

## 5.3 Device enrollment

Mesh enrollment requires an authenticated flow that creates or registers a unique device identity and receives explicit account authorization.

Conceptually:

```text
Verified Account
      |
Authenticated Device Enrollment
      |
Unique Device Identity + Credential
      |
Explicit Authorization
      |
Mesh Membership
```

Each device is independently revocable.

## 5.4 Device cryptographic identity

Each enrolled device has independent cryptographic credentials. Private device key material remains protected on the device using suitable platform-secure facilities where available. The architecture must support credential rotation without unnecessarily changing stable device identity or destroying history.

The implementation must use established cryptographic/TLS primitives rather than inventing a custom crypto protocol.

## 5.5 Friendly name vs identity

A user-visible name such as `Doonchy-PC` is not an identity credential. Renaming the machine or changing hostnames should not implicitly create a new device authorization.

## 5.6 Connection paths

Mesh may support both:

- encrypted direct/LAN path where safe and available;
- authenticated relay/internet path.

Both paths use the same authorization model. Network proximity affects routing, not trust.

No unauthenticated local metrics endpoint may be exposed merely because devices share a LAN.

## 5.7 Remote projection boundary

Raw local `SystemSnapshot` data must never be uploaded wholesale by default.

The remote path is:

```text
SystemSnapshot
      |
RemoteProjection
      |
Privacy Allowlist
      |
Mesh Telemetry Envelope
      |
Authenticated/Encrypted Transport
```

Only explicitly allowed fields may leave the machine.

## 5.8 Default Mesh data

Normal Mesh monitoring may include approved summary classes such as:

- CPU utilization;
- GPU utilization;
- memory utilization/pressure;
- storage capacity/activity;
- network throughput totals;
- selected sensors where enabled;
- alerts;
- provider/SysIn health;
- OS/platform identity;
- hardware category/model;
- last-seen/presence state.

Normal Mesh overview should not require transmission of:

- full IP addresses;
- MAC addresses;
- usernames;
- process command lines;
- environment variables;
- file paths;
- open files;
- remote endpoints;
- browser/document details.

## 5.9 Per-device visibility

Each enrolled device may expose a configurable allowlist such as:

- System Summary;
- CPU;
- GPU;
- Memory;
- Storage;
- Network Rates;
- Processes;
- Sensors;
- History;
- Diagnostic Details.

This allows different privacy levels for a personal laptop, gaming desktop, family machine, or server.

## 5.10 Adaptive remote telemetry

Mesh must not stream every local render sample at 20 FPS.

The architecture uses adaptive remote cadence:

- low-rate summary for machine list;
- medium-rate detail when a remote machine is opened;
- higher permitted rate for actively inspected subsystem detail;
- cadence drops again when detail is no longer viewed.

Local rendering, local sampling, and Mesh sync remain independent.

## 5.11 Remote freshness and offline state

Remote metrics expose measurement age and transport/data age. Stale values must be explicitly marked.

Offline machines are a valid state and show last-seen time. Last-known identity may remain visible, but last telemetry must never appear live without clear historic/stale labeling.

## 5.12 Remote history

Mesh history is explicit, bounded, and retention-controlled. The design supports at least:

- None;
- Summary;
- Detailed.

Summary is the recommended default for enabled Mesh history. No indefinite cloud history is allowed by default.

Users must be able to clear remote history, remove a device, and apply documented deletion behavior.

## 5.13 Device removal and compromise

Removing/revoking a device must:

1. revoke device credentials;
2. terminate active Mesh sessions;
3. stop accepting telemetry;
4. remove the device from account authorization;
5. apply the selected history retention/deletion policy.

A revoked device continues to support local SysIn. Only Mesh access is removed.

Account/session tooling should expose active sessions and allow revocation.

## 5.14 Observation-only remote authority

The first Mesh protocol contains no generalized remote execution channel.

It must not define arbitrary endpoints for:

- shell execution;
- arbitrary command execution;
- process termination;
- restart/shutdown;
- file mutation;
- hardware tuning.

This is a protocol-level non-goal, not merely a hidden UI feature.

## 5.15 Mesh failure isolation

Mesh outage, account outage, relay failure, internet loss, remote-device failure, or Mesh software failure must never prevent local SysIn from working.

Local dashboard, local telemetry, local history, local Doctor, snapshots, and CLI remain operational. Only networked functionality may degrade.

## 5.16 Future authorization model

Although initial Mesh usage is same-account devices, the internal authorization boundary should ask whether a principal may view a device rather than hard-coding account-ID equality throughout the codebase. This preserves future options such as family/team/read-only sharing without shipping those features in V1.2.

## 5.17 Security testing families

Mesh certification must test at least:

- invalid credentials;
- revoked-device reconnect;
- replayed enrollment attempt;
- expired session;
- token/session revocation;
- malformed telemetry payload;
- oversized payload;
- unexpected metric type;
- stale/replayed telemetry;
- relay outage;
- LAN impersonation;
- credential rotation;
- device removal during connection;
- privacy-field leakage.

Security failures must fail closed.

# 6. Installation, Migration, Update, and Release Engineering

## 6.1 V1.1 relationship

The current V1.1 PowerShell implementation is a known functional migration source and proof-of-concept baseline. V1.2 is a native architectural replacement, not a cosmetic refactor.

V1.1 should remain intact and installable while the native V1.2 work is developed and certified. The team must not incrementally mutate the PowerShell core into a mixed-runtime architecture that jeopardizes the known-good baseline.

## 6.2 Development strategy

V1.2 should be built beside V1.1 on isolated branches/integration paths. `main` must remain intentionally supportable.

Large V1.2 work should not silently replace the existing user-facing install path before migration, rollback, and release-candidate gates are complete.

## 6.3 Vertical implementation phases

The recommended implementation order is:

1. Native executable shell and CLI composition root.
2. Universal telemetry contracts and device/metric model.
3. Windows x64 reference provider layer.
4. Native TUI framebuffer/diff renderer/capability engine.
5. Overview.
6. CPU, GPU, Memory.
7. Storage, Network, Processes, Sensors.
8. Doctor, Settings, Command Palette.
9. History, Alerts, Snapshots, structured output.
10. Installer, migration, update, rollback.
11. Additional platform providers and certification.
12. Mesh account/enrollment/remote projection/Machines dashboard.
13. Full release certification.

The implementation plan may decompose these further, but it may not invert dependencies in ways that violate the architecture.

## 6.4 Platform strategy

Windows x64 is the reference implementation because V1.1 and current live hardware provide an immediate migration/test target. However, Windows providers implement universal interfaces; core interfaces must not be disguised Windows APIs.

Universal architecture exists from V1.2 design inception. Platform certification is independent.

Target artifact families may include, as they become implemented and certified:

```text
win-x64
win-arm64
linux-x64
linux-arm64
osx-x64
osx-arm64
```

Compilation alone does not confer support status.

## 6.5 Packaging

Release packaging should be compact and self-contained without forcing a single executable when that would make native provider dependencies unsafe or brittle.

A release package may include:

```text
sysin executable
approved provider/native dependencies
licenseselease metadata
```

Stable artifacts carry:

- product version;
- channel;
- platform/RID;
- commit provenance;
- SHA-256;
- dependency inventory;
- license inventory;
- schema version;
- certification state;
- signing status where applicable.

An SBOM should be generated for Stable releases.

## 6.6 Supply-chain rules

- Every shipped artifact is hash-verified.
- Published release metadata is immutable.
- Dependency versions are pinned.
- No arbitrary runtime download of mystery DLLs.
- No PATH-dependent product runtime requirement.
- No silent replacement of immutable published release bytes.
- Signing is used where the platform/release infrastructure supports and requires it.
- Preview builds may be unsigned, but must never claim to be signed.

## 6.7 Version and channel semantics

Version, update channel, build type, and certification are separate concepts.

Channels:

- Nightly;
- Preview;
- Release Candidate;
- Stable.

Version examples:

```text
1.2.0-preview.1
1.2.0-rc.1
1.2.0
```

`Stable` means published, immutable, verified, and fully certified for the applicable target. It must never mean merely that an updater points at a branch.

Once `v1.2.0` is published, its bytes are immutable. A later defect requires a new version such as `v1.2.1`.

## 6.8 Transactional update

The update sequence is:

```text
Resolve release
-> validate manifest
-> download exact artifact
-> verify hash/signature
-> stage separately
-> pre-activation validation
-> atomic activation
-> bounded post-activation health check
-> commit update
```

If a pre-commit step fails, SysIn should roll back where safely possible.

The only known-good executable must not be overwritten before replacement validation.

## 6.9 Version-separated install model

The implementation may use a structure conceptually similar to:

```text
SysIn/
├── current/
├── versions/
├── data/
└── rollback/
```

The exact on-disk arrangement may be simplified if the implementation preserves atomic activation, version identity, unknown-file safety, and rollback.

## 6.10 V1.1 -> V1.2 migration

Migration must:

1. detect the V1.1 layout;
2. validate known SysIn files/config state;
3. preserve a known-good backup;
4. migrate supported configuration through a schema-aware migration;
5. stage native V1.2;
6. verify the new runtime;
7. activate atomically;
8. run post-activation health checks;
9. preserve rollback where possible.

Preserve supported user configuration and current-user command registration where compatible.

Do not blindly preserve obsolete runtime files, stale manifests, incompatible config keys, or unknown executable/script files as if they were official components.

Unknown user files in an install directory must never be recursively deleted simply because SysIn owns the directory.

## 6.11 Rollback

Rollback restores the prior known-good runtime and compatible configuration/activation metadata without silently destroying newer user data.

Config migrations should preserve recovery copies when schema compatibility requires it.

## 6.12 Update failure tests

Release testing must include:

- interrupted download;
- wrong SHA;
- corrupt archive;
- truncated artifact;
- invalid/incomplete manifest;
- wrong platform/RID;
- wrong version;
- invalid signature where signatures are required;
- disk full;
- locked files;
- activation failure;
- config migration failure;
- post-startup health failure;
- rollback failure.

Each case must leave the installation in a safe and understandable state.

## 6.13 Published-byte verification

Stable verification must hash and validate the exact bytes users download, not merely the bytes in a local source checkout.

This requirement is permanent and exists specifically to prevent a repeat of V1.1's source-vs-published line-ending integrity failure.

# 8. Diagnostics, Logging, Notifications, and Safety

## 8.1 Diagnostic journal

SysIn may keep a small bounded local diagnostic journal containing operational events such as:

- startup/shutdown;
- provider initialization/failure;
- timeouts/circuit breakers;
- renderer failure;
- configuration migration;
- update result;
- unexpected exception.

It must not become an unbounded telemetry log or silently record sensitive process data.

Logs are local, rotating, size/retention limited, and erasable. Deep tracing is explicit per-session.

## 8.2 Support bundles

A future/implemented `doctor --bundle`-style support artifact must use privacy-aware defaults and present/redact sensitive information before sharing where practical. Raw memory dumps require explicit user choice because they may contain sensitive content.

## 8.3 Notifications

In-dashboard alerts are the default. OS notifications are optional and off by default unless explicitly enabled.

Notification behavior requires deduplication, cooldown, escalation/resolution tracking, and sustained-condition logic to avoid alert storms.

## 8.4 Privilege model

Normal SysIn runs as a standard user.

If a metric requires more privilege, the UI reports that capability as unavailable/permission-required. Elevation must be explicit, temporary, capability-specific, and visibly indicated.

SysIn must not silently elevate, permanently change execution/security policy, or install a kernel driver merely to unlock optional telemetry.

# 9. Brand and UX Acceptance

## 9.1 Intended first reaction

When a user runs `sysin`, the visual experience should support two reactions in order:

> **“Whoa — this is running in my terminal?”**

followed immediately by:

> **“I can actually understand my system.”**

The first reaction gives SysIn personality. The second gives SysIn purpose.

## 9.2 Information-design rule

> **Every screen should maximize information comprehension per unit of attention, not merely information per unit of space.**

Color, motion, hierarchy, responsive composition, and interaction exist to reveal system state faster without sacrificing truth, accessibility, or performance.

## 9.3 Product-wide remote/local clarity

A remote machine view must never be visually ambiguous with the local machine. Remote machine identity, connection state, and data age are always evident.

## 9.4 No fabricated data

SysIn must never display made-up sensor values, fake health scores, fake aggregate GPU numbers, or cached remote telemetry as if it were live.
