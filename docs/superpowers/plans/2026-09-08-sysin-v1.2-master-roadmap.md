# SysIn V1.2 Master Implementation Roadmap

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement each detailed plan task-by-task. This roadmap does not authorize implementation by itself; each numbered workstream must have its own detailed plan and review gate.

**Goal:** Deliver the locked SysIn V1.2 Universal + Mesh design as independently testable, certifiable workstreams without destabilizing the working V1.1 PowerShell baseline.

**Architecture:** Build the native universal core and Windows x64 reference slice first, then expand depth, product systems, release engineering, additional platforms, and Mesh through stable contracts. Each workstream must produce usable software and must preserve the governing separation: providers measure, telemetry models truth, views present, Mesh projects only approved remote data.

**Tech Stack:** C# / .NET 10 LTS; self-contained platform artifacts; purpose-built terminal renderer; xUnit v3 for native tests; existing PowerShell V1.1 tests remain active until V1.1 retirement is separately authorized.

**Spec:** `docs/superpowers/specs/2026-09-08-sysin-v1.2-universal-mesh-design.md`

## Global Constraints

- Every applicable release-certification category must individually equal exactly 10.0/10; any lower, unknown, untested, or unresolved material finding is HOLD.
- Local SysIn remains local-first, account-optional, standard-user by default, and independent of Mesh availability.
- The V1.1 PowerShell runtime remains the known-good migration baseline until native migration/rollback is proven.
- The native runtime must not depend on PowerShell for normal product execution.
- Unknown telemetry is never represented as zero.
- Distinct physical devices remain distinct; multi-GPU values are never fabricated into a single aggregate percentage.
- Render cadence, telemetry sampling cadence, and Mesh synchronization cadence remain independent.
- Balanced mode defaults to a 20 FPS render target and reports measured actual FPS separately.
- The TUI is purpose-built around framebuffer/diff rendering, capability detection, responsive layouts, keyboard-first navigation, and optional mouse support.
- SysIn Spectrum color identity is mandatory; activity intensity and health severity remain separate semantics.
- No hidden always-on Mesh agent/service is authorized by the V1.2 design.
- The first Mesh protocol is observation-only and defines no generalized remote execution channel.
- Stable releases use immutable, exact-byte-verified artifacts; compilation or CI success alone never authorizes Stable.

## Workstream 1 — Native Core + Windows x64 Overview Vertical Slice

**Detailed plan:** `docs/superpowers/plans/2026-09-08-sysin-v1.2-native-core-windows-slice.md`

**Outcome:** A side-by-side native preview executable that proves the universal domain model, provider contracts, supervised telemetry pipeline, immutable snapshots, purpose-built TUI, Spectrum styling, responsive Overview, native CLI/JSON basics, and real Windows x64 CPU/memory/GPU identity/storage/network/uptime telemetry without modifying the installed V1.1 command.

**Exit gate:** Native preview runs on Windows x64, all native tests pass, V1.1 regression tests still pass, rendered Overview artifacts exist at required sizes, and Owner review authorizes the next workstream.

## Workstream 2 — Windows Telemetry Depth + Complete Local Pages

**Required detailed-plan scope:**

- CPU topology, heterogeneous-core distinctions, frequency, trusted thermal/power/throttle sources.
- Multi-GPU role resolution, Windows GPU engine utilization, NVIDIA/AMD/Intel provider modules as justified by trust/evidence.
- Memory pressure/composition, physical storage vs volumes, disk activity/latency, network adapter detail, process inspection, sensors/battery.
- Dedicated CPU/GPU/Memory/Storage/Network/Processes/Sensors pages including GPU Compare and Process Inspector.
- Provenance/freshness display and failure-state UX.

**Exit gate:** Every local detail page is functionally complete for the Windows x64 reference target and has synthetic + real-hardware evidence.

## Workstream 3 — Local Product Systems

**Required detailed-plan scope:**

- Validated configuration model and Settings UI.
- Named profiles: Eco, Balanced, Realtime plus custom-profile mechanics.
- Bounded live/persistent history.
- Evidence-based alerts and optional OS-notification hooks.
- Universal command palette.
- Snapshot text/JSON/Markdown/save formats and schema versioning.
- Diagnostic journal, tracing, Doctor health contributors, structured CLI exit/stdout/stderr contracts.
- Performance self-observation and adaptive load-control policy.

**Exit gate:** Local SysIn is a coherent product rather than only a dashboard; config/history/alerts/snapshots/Doctor/CLI operate over the same normalized system model.

## Workstream 4 — Packaging, V1.1 Migration, Update, Rollback, and Release Engineering

**Required detailed-plan scope:**

- Self-contained Windows x64 packaging and activation layout.
- V1.1 detection, backup, config migration, activation, health-check, rollback, unknown-file safety.
- Immutable release manifest and artifact-hash model.
- Transactional update/check/rollback commands.
- Exact published-byte verification.
- SBOM/dependency/license/provenance generation.
- Signing-status plumbing without falsely claiming signed status.
- Installer/uninstaller safety and corrupted/interrupted-update fault matrix.

**Exit gate:** A preview/RC can replace V1.1 transactionally and restore it safely on failure; exact distributed bytes are verifiable.

## Workstream 5 — Universal Platform Expansion

**Required detailed-plan scope:**

- Linux x64 reference providers and terminal/package behavior.
- macOS Apple Silicon reference providers and terminal/package behavior.
- Additional RIDs only when actually implemented/testable: win-arm64, linux-arm64, osx-x64.
- Platform capability mapping into the same metric vocabulary.
- Platform-specific secure storage, privilege behavior, package/signing strategy, terminal degradation, performance budgets, and certification reports.

**Exit gate:** Each target is independently labeled Preview or Stable according to its own evidence. No target is considered supported merely because it compiles.

## Workstream 6 — SysIn Mesh Foundation + Multi-Machine Dashboard

**Required detailed-plan scope:**

- Account/login boundary for Mesh without making accounts mandatory locally.
- Per-device cryptographic identity, explicit enrollment, revocation, session visibility, credential rotation.
- Direct/LAN and relay-capable authenticated transport contract.
- RemoteProjection privacy allowlist and per-device visibility policy.
- Adaptive remote summary/detail cadences and explicit data-age semantics.
- Offline/last-seen behavior, bounded remote-history policies, deletion/removal semantics.
- Machines dashboard and clearly marked remote-machine views.
- Observation-only protocol with no arbitrary execution/control endpoint.
- Mesh Doctor, cross-machine alerts, fault/security/privacy tests.

**Exit gate:** Mesh can be independently certified. Local Stable may exist while Mesh remains Preview/HOLD, but Mesh must never be presented as Stable until every applicable Mesh category reaches 10.0/10.

## Workstream 7 — Full Certification + First Official Stable Release

**Required detailed-plan scope:**

- Cross-category certification report generation.
- Mandatory rendered visual evidence for every major page/state/layout.
- Accessibility matrix, performance measurements, provider/platform matrix, migration/update/rollback evidence, security/privacy evidence.
- Exact Owner candidate package with version, commit, RID, hashes, and certification report.
- Real-machine review at realistic terminal sizes.
- Immutable tag/artifact publication only after Owner PASS.

**Exit gate:** Every applicable category is exactly 10.0/10, all mandatory evidence is verified, no material finding remains unresolved, Owner accepts the exact candidate, and only then is Stable published.

Workstreams 5 and 6 may proceed in parallel only after the local contracts they consume are stable and tested. Neither may force platform/network assumptions back into the universal core.

## Review Discipline

Each detailed plan must:

1. identify exact files/modules and interfaces;
2. use test-first steps with failing-test evidence before production code;
3. keep tasks small enough for independent review;
4. preserve V1.1 until the migration workstream proves replacement/rollback;
5. generate visual evidence for user-facing changes;
6. end in an explicit PASS/HOLD review rather than silently flowing into the next workstream.
